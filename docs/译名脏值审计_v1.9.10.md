## §1 三类脏值与实例

### §1.1 LLM 元话语泄漏

翻译模型把「我为什么这么译」写进了译文：

```
Debden     -> 德宾dden（地名保留英文，避免不准确的音译）
Harrowbeer -> 哈罗贝尔回答问题时，请注意提供的信息表明没有现成的
Lyzha      -> 利扎hya 说明
502nd Fortress -> 502步兵师 fortress 在这里应视为一种单位类型而非直译…
```

第三例（`502nd Fortress`）已在批次二随单位概念词统一修掉，前两例在批次三修掉。

### §1.2 原文残片 / 转义符残留

拼音式译文只替换了前半段，后半段留着原文；`\r` 之类的控制符被读成文字：

```
Debden     -> 德宾dden        （"德宾" + 原文剩余 "dden"）
Lyzha      -> 利扎hya 说明     （"利扎" + 原文剩余 "hya"）
Harrowbeer -> 哈罗贝尔回车符    （"\r" 被读成「回车符」）
```

### §1.3 缩写被当单词误读

同一批单位里 `Fin. Army`=芬兰集团军、`Fin. Infantry Division`=芬兰步兵师，但：

| 键 | 旧译 | 误读 | 现译 |
|---|---|---|---|
| `Fin. Air Base` | 结束。机场 | `Fin.` 当成 finish | 芬兰空军基地 |
| `HQ Hun.` | 司令部霍恩。 | `Hun.` 当成 Horn | 匈军司令部 |
| `Fin. Machine Gun Battalion` | .机枪营 | 前缀整段丢失 | 芬兰机枪营 |
| `5th Rail.` | 5号铁路部队。 | 句点进了译文 | 第5铁路部队 |

判据：同一缩写前缀在本表其它条目里已有稳定译法（`Fin.`=芬兰、`Hun.`=匈牙利），异常值即为误读。

## §2 处置

- 新增 `integration/fix_name_artifacts.py`：`DICT_FIX`（英文键→正译）与 `CELL_FIX`（脏单元格→正译）两张**精确值**表，同时写 jsonl（含 `.qa` 副本）与场景 CSV。不做模糊匹配，避免误伤正文。
- 落地：**16 jsonl 格 / 4 文件**（unit、place 及其 qa）+ **134 CSV 格 / 49 文件**（Locations 13、MapText 24、OBs 26、Units 22，另若干重复单元格）。复跑 `--check` = 0。
- CSV 写盘安全：保留 BOM 与行尾（`\r\n` / `\n`），用 `csv.reader(io.StringIO(text, newline=""))` 解析；写前对 188 个文件做「读入→序列化→字节比较」，全部往返一致才落盘。

## §3 守卫

`mod/finalize.py` 新增两道：

1. **Name-artifact guard**（词典层）：值命中 `最终译文|不在翻译范围|请注意|回答问题时|保留英文|避免不准确|回车符|换行符|hya ` 或「以中文句读开头」即 `SystemExit`。
2. **两层同步守卫**：调用 `integration/fix_name_artifacts.py --check`，jsonl 或 CSV 任一残留即失败。

口径细节：首版「半角句点开头即脏」把 `.50英寸防空机枪` 这类口径写法误杀 40 条；现规则只认「中文句读开头」或「半角句点后紧跟汉字」。

## §4 复现

& $py integration\fix_name_artifacts.py --check   # 0 = 干净；2 = 有残留

## §5 边界

- 只覆盖「已发现并命名」的 7 个键。同族风险仍在：任何由 LLM 生成、未经人工复核的译文都可能带元话语——本轮的守卫只能拦住**已知话术**与**句读形状**，拦不住「语气不对」。
- 场景 CSV 是历史生成物的快照（生成器 `integration/apply_scenario_translations.py` 依赖不存在的 `name_rules`，不可重跑），所以脏值必须就地修；jsonl 同步修是为了下次重建不回落。
- 未进游戏目验；判据是词典与 CSV 的静态核对 + `--selftest` 通过。
