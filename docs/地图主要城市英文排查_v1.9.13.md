# 地图主要城市变英文：排查、可行性与修复（v1.9.13）

> 结论先说：**数据层是完整的，师徽钩子不是原因。** 12 个原版剧本的 69,481 条地图标签英文在四套语言包里**精确命中 100%**、字体缺字 0；师徽钩子只改 0x3ef56e 一个调用点，和文本查表的两个调用点没有交集。问题只可能出在「绘制时没有拿到译文」这一层——要么引擎送来的键与词典键**形式不同**（字距/大小写/空白），要么地图标签**根本不走**这两个已挂钩的查表点。本版把前者修掉、把后者做成可判定，并给数据层加了一道永久守卫。

---

## 1. 现象与范围

- 现象：地图上的**主要城市名**显示英文；界面、单位名、编成表仍为中文（用户报告）。
- 背景：v1.9.12 修好陆军师徽后才出现，用户怀疑是师徽修复的「误伤」。
- 工程侧铁律：**不启动、不附加游戏**；本报告的全部结论来自静态取证、离线测试与文件层核对，实机部分留给用户一步验证（§8）。

## 3. 代码变动考古：v1.9.10 → v1.9.12 到底改了什么

- c0ba938（v1.9.12）的变更文件只有：docs/、README*、VERSION、mod/WitE2CN_Text.dll、mod/payload/crest_names.bin、payload/package.json、payload/checksums.json、build_crest_map.py、finalize.py 的师徽守卫。**没有** translations.*、**没有**字体、**没有** GuiFonts.json、**没有**任何 CSV 或 .scn。
- 用 git show 对比 v1.9.10 / v1.9.11 / v1.9.12 三份 translations.json：v1.9.11→v1.9.12 仅 1 个值（Folgore 引号）；v1.9.10→v1.9.12 仅 4 个值（外加 F/G/H 三个军群名）。**键与地名一条未动。**
- 因此「地图城市变英文」若真由版本引起，只可能来自 **DLL 行为**，不可能来自词典/字体/数据。

## 4. 师徽误伤评估：没有因果通道

静态反汇编（游戏镜像转储，基址 0xaa0000，RVA 均为镜像内偏移）：

1. **文本查表**：0x456ef0 的签名全镜像唯一；.text 里指向它的 E8 只有两个，都在格式化函数 0xeda270 内（0xeda36f、0xeda861）。查表对象是 0x113bca0。
2. **师徽加载**：0xe8f56e 处 call 0xeedc30，目标校验通过；加载器开头 sub esp,0x400，ret 不带参数，调用点 add esp,0x18——**6 参 cdecl**，与 thunk 的 int __cdecl (const WCHAR*,void*,unsigned,int,int,int) 完全一致。
3. **交集为零**：师徽调用点不在两个文本查表点里；全镜像 .data/.rdata 里**没有任何**指向查表函数/格式化函数的函数指针，因此也不存在「师徽钩子把某个指针改坏」的通道。
4. **状态不共享**：文本表 table/pool 与师徽表 crest_table/pool2 是两组独立堆块；师徽线程只写自己的全局量，文本热路径只读文本表。

结论：**师徽修复不可能改变任何一次文本查表的结果**。把师徽钩子回滚不会修好地图；反而会丢掉刚修好的师徽。

## 5. 过去「地图是中文」是怎么实现的

- 地图标签的英文源在 MapText.csv / 场景数据里；引擎绘制时用**同一套本地化查表**（0x456ef0）取译文，钩子把查表结果换成词典值。
- 因为地图标签在 CSV 里经常是**字距拆开**的（"M o s c o w"、"B a y  o f  B i s c a y"），词典里有 365 条这种带空格的键；历史上还专门处理过「字距拆开的地名键 55 条」和「地图标签 121 个英文 → 0」。
- 这套链路对键的要求是**逐字符精确匹配**：Moscow、M o s c o w、MOSCOW、M o s c o w␠ 在旧钩子眼里是四个不同的键。只要引擎送来的形式与词典不完全一致，就原样返回英文——而界面文字通常不会带字距，所以表现为「只有地图标签是英文」。

同时发现一处**安装目录不干净**：

- Dat\CSV\1941 Campaign - No Early End\MapText.csv 是 **2026-10-24 15:16** 被换成的中文版（5,714 / 5,782 格中文，且含 奥波莱ń、_globino_、片假名等旧脏值），不是游戏原版。
- 这是早期「编辑器 CSV 导入」实验的遗留，**违反本项目「不修改原游戏 CSV」的铁律**。它不影响其余 12 个剧本的覆盖结论；如果引擎读这份 CSV，该剧本会显示旧脏中文而不是英文——与本次「主要城市英文」的现象相反。
- 建议用 Steam「验证文件完整性」把这一份 CSV 还原；本工具会把它标成 WARN，不参与覆盖统计，也不阻断构建。

## 7. 修复：数据层守卫 + 运行时键归一化 + 只读探针

### 7.1 数据层（永久守卫）

- 新增 integration/check_maptext_coverage.py，finalize.py 在师徽守卫之后调用；任何一条英文标签在任一语言包查不到、或字体缺字，**拒绝出包**。
- 判据与运行时完全一致（精确 → 归一化唯一键），避免「脚本绿、游戏里英文」的两套标准。

### 7.2 运行时（mod/src/text_hook.c）

- 新增**第二索引**：把 72,251 个键按「去掉空格/制表/NBSP/全角空格 + ASCII 小写」折叠后再建一张哈希表；精确表仍是权威，**只有精确未命中时**才查第二索引；同一折叠键对应两种译文时整键停用（返回 NULL），绝不猜。
- 这样 Moscow / M o s c o w / MOSCOW / "M o s c o w␠" 会落到同一条译文；对界面文字没有影响（精确命中的路径一行没改）。
- 新增**只读探针**：每次查表先对 8 个主要城市（moscow/berlin/leningrad/stalingrad/kiev/kharkov/odessa/sevastopol）的归一化键做一次比较，命中一次写一行 PROBE map label lookup: <name> 到 logs/native.log。它只写 8 行，不改变任何返回值，用来判定「地图标签到底有没有走这个查表入口」。

### 7.3 为什么不动师徽钩子

第 4 节已证明它没有因果通道；改它只会新增风险。本版对师徽的**唯一**要求是：文本钩子安装顺序不变（load_map → install_calls → CreateThread(crest)），师徽逻辑一字未改。

## 8. 核查：怎么确认修好了、且没有新问题

### 工程侧（已执行，见交付记录）

1. **DLL 离线自测**（合成镜像，不加载游戏）：PASS: decoy skipped; 2 text call sites; 10000 thiscall round-trips; crest path restored; map-label variants normalized; unrelated paths unchanged。
   - 新增断言：MOSCOW、  M O S C O W  必须归一化到 莫斯科；无关文本 Unrelated Label 必须原样返回。
2. **地图标签覆盖**：四语言包 69,481 / 69,481 命中，缺字 0。
3. **finalize 全守卫**（含新增地图标签守卫）与 **checksums** 全通过。
4. **发布**：publish.py 复制后按 checksums 逐文件校验；安装目录 package.json 版本与仓库一致。
5. **离线 selftest**：WitE2CN.exe --selftest 四语言包物化 PASS（不启动游戏）。

### 实机侧（用户一步验证）

1. 启动 mod\WitE2CN.exe，进一个剧本，看地图城市名。
2. 退出后看 mod\logs\native.log：
   - 有 PROBE map label lookup: moscow（或其它城市） → 地图标签**确实走**这个查表入口。若城市已是中文，说明键形变体就是原因；若仍是英文，把该行与截图发回，说明还有第三种键形。
   - **没有任何 PROBE 行** → 地图标签**根本不走**这两个查表点（旁路绘制）。下一步不是继续调词典，而是挂地图文字绘制/加载函数（第 9 节 C 方案）。
3. 回归项：界面中文、单位详情页师徽、编成表、事件文本与 v1.9.12 一致；地图无黑格、无乱码、无卡顿。

## 10. 未做与风险

- **未实机**：本版全部结论来自静态取证与离线测试；地图最终是否变中文，取决于 PROBE 结果（§8）。
