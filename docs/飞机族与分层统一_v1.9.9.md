## 4. Airframe 统一（58 条）

改前 9 种写法并存：`IL-2 Airframe`（英文原样）、`伊尔-2 Airframe`（半译）、`P-51 机体`、`CR.42 机体`、`*** AIRFRAMES ***`→「*** 飞机型号 ***」等。

定稿规则：**「<该机在词典里的机名>机体」**，机名不存在时保留拉丁型号。例：

- `Bf 109 Airframe` → `Bf 109机体`
- `IL-2 Airframe` → `伊尔-2机体`
- `P-51D Airframe` → `P-51D 机体`
- `He 111 Airframe` → `He 111机体`
- `*** AIRFRAMES ***` → `*** 机体 ***`

58 条全部登记在 `glossary/equipment_name_fixes.json`（其中 40 条原本连词条都没有，靠修订表的 `add: true` 补进 jsonl）。

## 5. 分层统一：为什么「改了一个地方」游戏里不变

字典是逐层赋值，后面的覆盖前面的：

1. `data/**/translations/*.zh.jsonl`（语料层：equipment / unit / place / event / hotkey / ui_full…）
2. `build/scenario_csv_zh/**/*.zh.csv`（14 个剧本的单元格）
3. `glossary/reference_overrides.json`（terms < places < ui）
4. `glossary/manual_translations.json`
5. `glossary/master_overrides.json`（**最后套用，压掉以上所有层**）

v1.9.8 时发现 `integration/fix_equipment_names.py` 按 `(source, old)` 匹配——同一装备同时出现在 `Devices.csv` 与 `Ground.csv`，修订表只点名 `Ground.csv` 时，jsonl 里 `source=Devices.csv` 的行不改。Jagdpanzer 家族就是这样「改过但没生效」。

本轮修的机制：

- `fix_equipment_names.py` 改为**只按英文原文匹配**；同一原文被要求两个不同译文时直接 `SystemExit`。
- 新增 `glossary/layer_unify.json` + `integration/unify_layers.py`：一条规则同时写 jsonl（含 `.qa`）、场景 CSV、`reference_overrides.json`（及 `manual_translations.json`），四种动作 `set / revert / drop_override / adopt_override`。
- `integration/audit_layers.py` 做三层比对，`--check` 对「覆盖层 ≠ 下层」硬失败；已接进 `mod/finalize.py`（每轮构建必跑）。

## 7. 局限

- **1,816 组「同词多译」未处理**：同一英文串在不同语境有不同译法（如 `Group` 既是「大队」也是「集团」），`audit_layers` 只报告不失败。要处理必须先有「按上下文分列」的数据结构，属结构性工作，不宜在本轮硬改。
- **译名主观项**：`VL Myrsky`（芬兰语「风暴」）保留拉丁原名而非音译；`Hedgehog` 取「刺猬」而非「豪猪」。这类没有权威出处，按「保留型号可辨识性」处理。
- **498 个未译飞机名不是遗漏**：它们是 `Bf 109G-6`、`Ju 88A-4` 这类纯型号，保留原文比强行音译更有用。
- `airframe` 修订表里有 82 条（多于 CSV 实际的 58 条），多余条目匹配不到任何单元格，属无害冗余。
- 工程侧按铁律**不启动游戏**，以上均为静态核对与离线自检，实际显示需玩家进游戏确认（看飞机列表里 `IL-2M` 是否显示为「伊尔-2M」、生产面板里 Airframe 是否都是「…机体」）。
